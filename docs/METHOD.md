# 方法：和 Agent 一起做汇报 deck

这套方法来自一次真实的汇报 deck 制作：从一份纯文字的商业计划书开始，经过十几轮修改，做成 50 多页图文 deck。修改涉及主次调整、数据口径、措辞、品牌、新增页面、换导出方式。下面是那次留下来的做法。

适用场景：需要反复修改、会被不同的人审、数据要经得起追问的 deck，比如融资、汇报、方案、发布。一次性的小分享不需要这么重。

## 一、分工

| 人 | Agent |
|---|---|
| 提供资料，说清楚给谁看、要达到什么目的 | 读完全部资料，写叙事主线和逐页大纲 |
| 确认叙事主线：先讲什么、后讲什么、哪里是重点 | 按大纲用组件排页面，每轮自己截图检查 |
| 拍板有冲突的口径：数据怎么写、措辞能不能用、哪些审阅意见不采纳 | 派子 Agent 扮演听众审阅，整理问题清单，按决定修改 |
| 在网页上直接改字 | 改结构、改版式、补页面，不覆盖人改过的字 |

原则：Agent 提方案和问题，人做取舍。凡是“这个说法能不能讲”“这个数要不要放”的问题，都应该交给人。

## 二、六步工作流

### 1. 资料进仓库

把原稿、会议纪要（字幕或文字稿）、数据报告放进 `sources/`。Agent 只依据仓库里的原件写，不依据对话里的转述，也不凭记忆。

- `sources/` 默认在 `.gitignore` 里。仓库要公开时，资料不会被带出去。
- 会议纪要往往比原稿更重要：原稿里写的是结论，纪要里有“为什么这么写”和“听众真正在意什么”。

### 2. 叙事主线

在 `deck/narrative.py` 写几段话：一句话总述（THESIS），每一段讲什么、讲述重点是什么。在工作台的“叙事与大纲 → 叙事主线”里给人确认。

这一步最容易省掉，也最容易导致返工。实际案例：deck 做到第三版，负责人指出“重点应该是前面的合作方案，而不是后面的技术底座”，结果有 23 页要压缩、11 页要新增。如果一开始就把叙事主线交给人确认，这次返工可以避免。

### 3. 逐页大纲

每页只写一个主张，并说明用什么画面来表达。大纲不单独维护：写在 `deck/deck.py` 每个 `S()` 调用的 `notes`（讲述要点）、`visual`（画面）、`origin`（依据）里，工作台会自动汇总成“逐页大纲”。

### 4. 页面

用 `tools/components.py` 的组件拼页面。要求：

- **以图为主。** 截图、架构图、流程图、概念图都可以，不要连续出现纯文字页。
- **版式要变化。** 同一种版式不要连用三页。
- **一页一句标题。** 标题直接说结论，比如“每上一个项目，就来一波新用户”，不要只写“用户增长”。
- **数字要有出处。** 数字放在页面上，口径写在讲稿（notes）里，方便被追问时回答。

### 5. 角色审阅

每完成一版，派子 Agent 扮演听众挑毛病。给审阅 Agent 的输入包括：逐页截图（`.qa/*.png`）、讲稿（工作台导出的大纲）、原始资料，以及**完整的背景**。

背景要写清楚：

- 听众是谁，他在意什么。比如“只看图和数字”“最在意自己能得到什么”。
- 利益关系。实际案例：汇报对象是方案里一个合作产品的出资人。审阅 Agent 拿到这个背景后发现，方案对这个产品用了“改版、重构还是重做”的措辞，读起来像在说它不行。作者自己完全没意识到这个问题。
- 要求的输出格式：按严重程度排序，每条写清页码、问题、改法；最后列出听众当场会追问的问题。

建议至少两个角色：一个是**听众**（出资人、老板、客户），一个是**原意守护者**（读完会议纪要，检查作者和负责人的意思有没有讲到、有没有讲错）。技术类内容再加一个**事实核对者**，负责核对哪些已上线、哪些是规划、数字是否准确。

### 6. 修订留痕

在 `deck/versions.py` 记一版：改了什么，以及提出的每个问题（提问人、问题、处理）。**没采纳的也要记，并写明原因**。比如“未改：负责人已定 BP 原话照用”。

这样下一轮审阅的人能看到哪些问题已经讨论过、为什么那样定，不用重复争论。

## 三、六条原则

1. **资料先进仓库。** 只依据原件写。
2. **以图为主。** 不连续放纯文字页。
3. **示意和真实分开。** 自己画的界面示意图标上“示意”。示意图里不要出现像真实统计的数字（在线人数、奖池金额），否则会被当成造假。
4. **口径写进讲稿。** 每个数字从哪来、怎么算的，写在 notes 里。
5. **先想听众是谁。** 同一份数据，对出资人和对技术同事讲法不同；涉及听众自己的项目，措辞要格外小心。
6. **人定取舍。** 审阅意见之间、审阅意见和负责人的决定之间有冲突时，交给人决定，并记进版本记录。

## 四、三种图怎么分工

| 类型 | 谁来做 | 要求 |
|---|---|---|
| 示意图、架构图、流程图、手机界面示意 | Agent 用 HTML/SVG 画 | 可编辑、跟随配色；界面示意标“示意” |
| 概念图（章节页、愿景页） | 图像模型 | 在 `concept(key, label, prompt)` 里写提示词，全套统一风格（配色、材质、留白方向），生成后放 `assets/concept/<key>.jpg` |
| 截图 | 来自真实产品 | 证明“已经做出来了”；演示数据要注明，不能当业务规模 |

概念图的提示词在构建时汇总到 `deck-content.json` 的 `conceptPrompts`，可以整批交给图像模型生成。图还没生成时页面显示占位，不影响排版。

## 五、自检

每轮修改后：

```sh
tools/qa-shots.sh      # 逐页截图到 .qa/
tools/qa-sheet.sh      # 每 12 页拼一张联系表
```

Agent 看联系表，检查：文字溢出或重叠、页面下半部分空白过多、图片没加载、品牌或 logo 用错、旧样式盖住新内容、连续的纯文字页。

实践中自检发现过：收尾页大标题被旧样式隐藏；改了默认文字但页面没变（JSON 里还是旧值，见下文“默认值跟踪”）；示意图里的数字看起来像真实统计；logo 用了错误的版本。

## 六、和工具相关的几条约定

- **文字的唯一来源是 `deck-content.json`。** 网页编辑写它，构建读它。Agent 改 `deck.py` 里的默认文字时，构建会判断这个字段有没有被人改过：没改过就跟随新默认值，改过就保留人的版本。
- **不要手动删 JSON 里的文字键来“刷新”默认值**，否则会冲掉人的修改。
- **页码不要写死。** 目录和章节跳转用 `data-chapter="页面 id"`，构建时会换成真实页码。
- **导出用工具自带的功能。** 发 PDF 用“导出 PDF”（16:9，与屏幕一致）；发可编辑版本用“导出网页”。
